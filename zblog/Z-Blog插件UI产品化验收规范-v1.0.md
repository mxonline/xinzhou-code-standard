# Z-Blog 插件 UI 产品化验收规范 v1.0

本规范是 `Z-Blog插件完整开发流程-v2.0.md` 的强制补充规范，适用于包含后台页面、表格、筛选、图表、Drawer、AJAX、移动端或可视化交互的所有 Z-Blog PHP 插件。

目标：防止“功能能运行、CI能通过，但后台仍像开发页面/AI生成页面”的情况进入正式发布。

## 一、在完整流程中的位置

UI 相关任务必须同时经过两层门禁：

1. **T3 / UI 实现阶段：产品化实现门禁**
2. **T5 / Release 前：最终 UI 实机验收门禁**

不得把“页面能打开”“无 Fatal/SQL Error”“CSS 文件存在”“CI PASS”替代 UI PASS。

任何一项 UI 硬门禁 BLOCKED：

- T3 不得判完整 PASS；
- T5 不得 PASS；
- Release Gate = BLOCKED；
- 禁止 Tag / Release / 正式 ZIP。

## 二、真人产品团队三角色审查

每个正式后台模块至少从以下三个视角复核：

### 产品经理视角

- 模块命名是否符合站长习惯；
- 信息层级是否按“先看结论 → 再看原因 → 再看详情”组织；
- 是否把数据库查询顺序直接变成页面结构；
- 是否存在功能有了但用户不知道用途的区域；
- 是否知道下一步可以点击哪里继续分析。

### 前端 / 交互视角

- 表格、筛选、按钮、分页、Drawer、图表、空状态是否自然；
- 主要操作是否始终可见；
- 是否存在依赖横向滚动才能操作；
- PC / 平板 / 手机是否合理响应；
- 文本是否溢出、重叠、被遮挡；
- 加载、错误、空数据状态是否完整。

### 普通 Z-Blog 站长视角

- 不看 PRD、不看源码，是否能理解页面；
- 技术指标是否先给中文含义；
- 内部字段、英文枚举、数据库名是否暴露；
- 空值是否有业务含义；
- 页面是否存在明显 AI/开发占位文案。

## 三、UI 文案与字段语义硬门禁

禁止正式界面直接出现：

- `字段 1 / 字段 2 / 字段 N`；
- 数据库字段名；
- PHP/JS 内部变量名；
- 函数名、migration/state 等开发概念；
- `direct/search/social/external/desktop/mobile/tablet` 等内部枚举原值；
- `Path / Referer / Browser / Device / AI crawler` 等裸英文开发术语；
- “下钻”等未做用户语义转换的分析术语；
- AI 式免责声明、说明书式长句。

允许保留 PV / UV / IP / UTM / RUM / LCP / INP / CLS / TTFB / FCP 等行业通用缩写，但必须有中文业务上下文或帮助说明。

### 空值规范

禁止所有缺失数据统一显示 `-`、`NULL` 或空白。

必须根据语义显示，例如：

- 无 Referer → `直接访问` / `无来源`；
- 真人访问无蜘蛛名 → `非蜘蛛`；
- 浏览器无法识别 → `未识别浏览器`；
- 升级前无历史字段 → `升级前无此数据`；
- Beacon 未开启 → `尚未开启页面性能采集`；
- 真正无数据 → `暂无数据`。

## 四、表格布局硬门禁

普通业务列表不得依赖横向滚动才能完成主要操作。

### 桌面列表原则

主列表只保留核心字段；次要字段进入 Drawer / 详情页 / 折叠区域。

禁止通过固定大 `min-width` 强制撑宽普通业务表格，例如：

```css
min-width: 1320px;
```

除确属数据矩阵类页面，否则不得使用这种方式作为默认布局。

### 操作列

`详情 / 查看记录 / 查看来源 / 编辑 / 删除` 等主要操作必须在常用宽度下始终可见，不能要求用户先横向滚动到最右侧。

### 响应式最低验收宽度

至少实机或浏览器真实视口验证：

- 1366px
- 1024px
- 768px
- 390px

检查：

- 是否出现不必要横向滚动；
- 核心信息是否可见；
- 主要操作是否可见；
- 是否文字重叠/裁切；
- Drawer / 弹层是否正常；
- 页面是否被撑破。

移动端优先卡片、折叠或纵向详情，不要求硬塞完整桌面表格。

## 五、详情 Drawer / 详情页门禁

详情数据必须使用明确字段结构绑定，禁止通过 `<td>` 顺序或 DOM 文本顺序猜字段。

字段名必须使用真实业务语义。

设备类型等内部值应转换为用户可读中文，例如：

- desktop → 桌面设备
- mobile → 手机
- tablet → 平板

HTTP 状态码建议提供简短说明：

- 200 → 正常
- 301/302 → 跳转
- 403 → 禁止访问
- 404 → 页面不存在
- 500 → 服务器错误

## 六、性能与专业指标页面

技术指标不能只写缩写或内部字段。

示例：

- DurationMs → 服务器响应耗时
- LCP → 主要内容显示速度
- INP → 页面操作响应速度
- CLS → 页面稳定性
- TTFB → 首字节响应时间
- FCP → 首屏内容出现时间

P75 等统计学表达若保留，必须在帮助说明中解释，例如：`75% 的访问快于该数值`。

## 七、测试数据隔离

开发验收产生的 `/__xz_*`、`/v3-*`、`/_xz_*` 等测试路径：

- 不应成为正式产品验收截图的主要展示数据；
- 不得删除真实历史数据；
- 可在 UI 中提供“隐藏测试数据”能力；
- 最终验收优先使用首页、文章页、真实 404、真实 Referer 等正常访问场景。

## 八、最终 UI 验收证据

UI PASS 必须有真实证据，至少包括：

- 实际打开本机 Z-Blog 后台；
- 所有正式模块逐页检查；
- 典型数据场景；
- 1366 / 1024 / 768 / 390 四类宽度；
- 记录发现的问题与修复结果。

项目可维护：

```text
docs/<version>/ui-semantic-audit.md
```

建议记录：

- 页面；
- 问题；
- 修改；
- 空状态；
- 术语转换；
- 响应式结果；
- 实机证据；
- PASS / BLOCKED。

## 九、T3 与 T5 判定

### T3 UI PASS 必须同时满足

- 功能可用；
- 文案/字段语义通过；
- 页面信息架构通过；
- 表格布局通过；
- 响应式通过；
- Drawer/详情通过；
- 空状态/错误状态通过；
- 本机真实页面验证通过。

### T5 Release 前再次复核

T5 必须重新检查：

- 新增/修改页面是否仍符合本规范；
- 是否有开发占位符回归；
- 是否有宽表横向滚动回归；
- 主要操作是否可见；
- 技术术语是否被重新暴露；
- 移动端是否仍正常。

任何一项失败：

```text
UI Product Gate = BLOCKED
Release Gate = BLOCKED
```

不得发布。
