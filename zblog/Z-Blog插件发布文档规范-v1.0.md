# Z-Blog 插件发布文档规范 v1.0

本规范属于《Z-Blog 插件完整开发流程 v2.0》的正式发布门槛。插件只有在发布文档与真实代码状态一致、并且文档像真实项目维护者写作时，才允许进入 Tag / GitHub Release。

## 1. 必备发布文档

每个正式版本默认检查并维护以下文档：

- `plugin.xml`：插件 ID、名称、版本号、兼容 PHP/Z-Blog 信息、发布日期等插件元信息。
- `README.md`：当前正式版本、功能概览、安装方式、后台入口、使用说明、注意事项与文档索引。
- `docs/CHANGELOG.md`：按版本记录新增、优化、修复、兼容性变化和测试结论。
- `docs/VERSION.md`：当前版本状态、版本路线、已发布版本与下一版本方向。
- `docs/RELEASE_NOTES_vX.Y.Z.md`：本次正式版本发布说明。

如果仓库目录结构不同，可使用等价文件，但必须保证上述信息完整且可追溯。

## 2. 文档必须采用真实维护者写法

插件文档不是为了“填满模板”，而是让真正准备安装、升级、维护插件的人快速看懂当前版本。

默认写作原则：

- 只写真实存在、真实完成、真实验证过的功能和状态。
- 优先写用户会实际遇到的问题：插件做什么、怎么装、怎么用、升级会不会影响旧数据、哪些地方需要注意。
- 使用具体名称、页面、字段、版本号、限制和行为，不写“全面升级”“大幅优化”“强大功能”“更智能”等空泛宣传语。
- 不机械使用“本版本主要围绕……进行全面优化”“进一步提升用户体验”“显著增强稳定性”一类 AI / 模板化句式。
- 不把每个小修改都包装成重大特性；修 Bug 就明确写修了什么 Bug、影响什么场景。
- 不虚构开发过程、测试环境、用户反馈、实测经历或性能提升数字。
- 测试结论必须有真实测试或 CI 证据；没有验证的项目直接写“未验证”“待实机验证”或“当前环境未覆盖”。
- 已知限制必须保留，不能为了让发布说明看起来漂亮而隐藏。
- README 面向使用者；CHANGELOG 面向版本差异；VERSION 面向维护状态；Release Notes 面向本次升级。四者不要复制同一段话。
- 语言保持自然、简洁、像插件作者或维护者本人写的说明，不追求整齐到失真的固定句式。

### 推荐表达

例如真实修复说明：

> 修复隐私设置中 IP 保存模式选中状态显示错误的问题。该问题只影响后台回显，不改变已经保存的配置值和历史访问记录。

而不是：

> 全面优化隐私设置模块，进一步提升用户体验和系统稳定性。

例如真实兼容说明：

> 本次没有修改访问日志表结构，v1.2.0 已有数据可直接继续使用。

而不是：

> 全面兼容历史版本，无缝升级，使用更放心。

## 3. Release Notes 最低内容

`docs/RELEASE_NOTES_vX.Y.Z.md` 至少包括：

- 版本号与发布日期
- 本版定位
- 新增功能
- 重要优化
- Bug 修复
- 数据库 / Hook / 配置变化
- 向后兼容说明
- 升级注意事项
- 已知限制
- 测试与 CI 结论
- 安装包文件名
- 对应 Tag / GitHub Release

没有真实执行证据的测试不得写成“已通过”。如果某一栏目本版本没有内容，可以省略，不为了套模板强行补齐。

## 4. 条件性文档

以下情况自动增加对应说明：

- 数据库结构或迁移发生变化：增加升级 / 迁移说明，可使用 `docs/UPGRADE_vX.Y.Z.md`。
- 存在不兼容变化：必须增加 Breaking Changes 与回退方案。
- 新增复杂配置项：README 或独立配置文档中增加配置说明与默认值。
- 安装 / 卸载行为变化：说明数据保留、删除策略与风险。
- 安全修复：说明影响范围和升级建议，但不得泄露可直接利用的攻击细节。

## 5. 发布文档一致性检查

发布 Dry Run 必须核对：

- `plugin.xml`、README、VERSION、CHANGELOG、Release Notes 的版本号一致。
- 发布日期一致或符合仓库约定。
- README 所称“当前正式版”与实际 Tag / Release 状态一致。
- CHANGELOG 中本版本状态与实际发布状态一致。
- Release Notes 中列出的功能与真实 Diff / PR 一致。
- 数据库、Hook、配置变化已写明。
- 升级要求、兼容范围和已知限制没有遗漏。
- 安装包名称与版本一致。
- 不存在把“待验证”“计划中”写成“已完成”的状态漂移。
- 文档中没有明显模板堆砌、AI 套话或与本插件无关的泛化描述。

任一关键版本信息冲突或存在虚假完成状态，Dry Run 直接判定为“不可发布”。

## 6. GitHub Release 文案

GitHub Release 默认使用 Release Notes 的精简版，至少包含：

- 版本主题
- 主要新增 / 优化 / 修复
- 升级注意事项
- 兼容性说明
- ZIP 安装包
- CHANGELOG / 完整 Release Notes 链接

Release 文案也必须采用真实维护者写法，避免只写“update”“fix bugs”，也避免把小版本写成营销软文。

## 7. 发布后的文档回写

GitHub Release 真正创建成功后，自动回写：

- README：当前正式版本
- VERSION：版本状态改为已发布
- CHANGELOG：本版本状态改为正式发布
- Release Notes：补充最终 Tag / Release / 包名
- Notion：记录版本号、Tag、Release、Commit、CI、发布日期和发布包状态

如果 Release 未真正创建，以上状态不得写成“已发布”。

## 8. 正式发布闭环

```text
代码与测试完成
→ 读取真实 Diff / PR / 测试结果
→ 用真实维护者写法更新插件文档
→ 文档一致性与去模板化检查
→ 发布 Dry Run
→ 合并主分支
→ 创建 Tag
→ 创建 GitHub Release
→ 附加正式 ZIP
→ 回写 README / VERSION / CHANGELOG / Release Notes
→ 同步 Notion
→ 标记已发布
```

本规范不包含上传 Z-Blog 应用中心；除非用户另行明确要求，否则“正式发布”默认指 GitHub Release + 正式 ZIP 包 + 插件文档同步。
