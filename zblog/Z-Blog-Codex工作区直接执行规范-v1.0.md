# Z-Blog Codex 工作区直接执行规范 v1.0

本规范定义《Z-Blog 插件完整开发流程 v2.0》的首选执行架构。

## 核心原则

完整开发流程应尽量直接运行在**能够同时访问真实代码仓库和终端的 Codex 工作区**中，而不是通过额外的本地 Runner 再间接调用 Codex。

目标体验：

```text
用户只提出需求
→ ChatGPT 恢复项目、设计需求、更新 PRD 与验收标准
→ Codex 直接进入真实项目工作区
→ 读取 AGENTS.md / PRD / 当前代码
→ 修改真实代码
→ 运行本地测试
→ 必要时直接验证本机 Z-Blog / PHP / 数据库 / Nginx
→ 失败自动修复并复测
→ Git Commit / Push / CI
→ 插件文档 / Release Dry Run / GitHub Release
→ Notion 回写
```

正常开发过程中，用户不应再负责复制提示词、创建 task.json、手动启动 Runner、逐条执行测试命令或反复截图确认。

## 职责划分

### ChatGPT

负责：

- 恢复 Notion / GitHub 项目状态；
- 分析用户需求或提出产品设计需求；
- 生成/更新 PRD、技术边界和验收条件；
- 判断是否需要数据库、Hook、性能、安全或兼容性检查；
- 核验 GitHub Commit / CI / Release 和 Notion 状态；
- 保证“已执行/已规划/外部阻塞”状态真实。

### Codex 工作区

负责真实执行：

- 读取当前 Git 工作树；
- 编辑源码；
- 执行 PHP、PowerShell、Composer、PHPUnit、Git 等命令；
- 访问本机测试站；
- 验证 Z-Blog Hook、数据库升级、访问采集、后台页面等运行时行为；
- 读取开发日志；
- 普通失败自动修复并复测；
- Commit / Push；
- 有权限时查看 GitHub CI 并修复失败。

Codex 工作区就是开发执行环境，不再要求另外一层代理转发普通开发任务。

### GitHub

源码、分支、Commit、PR、CI、Tag 和 Release 的事实来源。

### Notion

长期保存 PRD、项目状态、关键架构、数据库/Hook变化、复杂故障、测试结论与发布记录。

## 工作区要求

理想工作区同时具备：

- 目标插件真实 Git 工作树；
- Git 与 GitHub 权限；
- PHP CLI；
- 本地 Z-Blog 测试站；
- 本地数据库访问能力；
- Nginx/PHP FastCGI 等实际运行环境；
- 项目 `AGENTS.md`；
- 自动测试与本机验证脚本。

对于 Windows Z-Blog 开发，推荐让 Git 工作树直接位于实际测试站的：

```text
<Z-Blog Root>\zb_users\plugin\<plugin_id>
```

这样 Codex 修改代码后即可直接在同一套 Z-Blog 中验证，不需要复制插件文件到另一个目录。

## AGENTS.md 要求

每个正式维护的插件仓库应有项目级 `AGENTS.md`，至少说明：

- 项目定位；
- 当前版本状态以哪些真实文件为准；
- 代码边界；
- 数据库兼容规则；
- 何时必须本机实机验证；
- 默认测试命令；
- Git/CI 规则；
- 发布门槛；
- 状态真实性要求。

`AGENTS.md` 不应长期写死容易过期的“当前分支/当前版本”；如需写版本，必须明确真实来源优先级。

## 本机实机验证

以下任务默认必须在真实 Z-Blog 开发环境验证：

- 大版本升级；
- 数据库创建、升级、迁移和索引；
- Hook 生命周期；
- 插件安装、启用、停用、卸载；
- 后台页面/AJAX/权限；
- Nginx/PHP FastCGI 相关行为；
- IP、UA、Referer、状态码、蜘蛛等真实请求采集；
- 高访问量采集与统计查询性能；
- 仅靠 CI 无法还原的兼容性行为。

CI 通过不能替代必须的实机验证。

## 自动测试脚本

每个项目应提供简单、可重复的本机入口，例如：

```text
scripts/local-verify.ps1
```

该入口负责可自动化的标准链路，例如：

- `git diff --check`；
- PHP syntax；
- PHPUnit；
- 本地 HTTP smoke；
- 必要的固定运行时检查。

更深的数据库、Hook、迁移和业务断言可以拆为独立脚本或由 Codex按项目测试规范执行，但必须留下真实结果。

## 无人值守原则

在授权的开发工作区内，Codex可以直接执行普通、可逆的开发操作，不应逐条要求用户确认：

- 编辑源码；
- 运行测试；
- 读取开发日志；
- 修复普通失败；
- 创建/切换开发分支；
- Commit / Push 开发分支；
- 读取并修复 CI。

只有以下情况需要停下：

- 缺少关键凭据或权限；
- 当前环境无法访问必须的资源；
- 操作涉及生产站、生产数据库或不可逆数据变更；
- 需求本身存在重大歧义且继续执行会产生高风险。

## Local Runner 的定位

`Z-Blog 本地无人值守开发执行器` 不再是主开发链路。

它可以保留为可选能力，用于：

- 定时任务；
- 远程触发一个没有持续 Codex 工作区的本机；
- 状态轮询；
- 特殊无人值守批处理。

当 Codex 已经直接运行在能够访问工作树和终端的环境里时，不应再额外套 Runner。

## 完成定义

对必须实机验证的任务，完成必须同时具备：

```text
代码已修改
+ 相关快速测试已执行
+ 本机 Z-Blog 实机验收已执行
+ 必要数据库/Hook/日志检查已执行
+ 失败已修复并复测
+ Git 状态明确
+ CI 状态明确
```

缺少其中的必需证据时，只能标记为“开发中”“待实机验证”或“外部阻塞”，不能标记完成。
