# Z-Blog 插件完整开发流程 v2.0

本流程是所有 Z-Blog PHP 插件开发、升级、修复、优化和重构任务的默认总控流程。

目标：用户只提出需求，ChatGPT 自动恢复项目状态、调用可用工具、组织 Codex 开发、测试、Git 版本管理、Notion 同步和发布准备，不再逐步询问“下一步”。

## 固定职责

- ChatGPT：需求分析、项目恢复、PRD、任务拆分、工具调度、结果检查和流程推进。
- Codex：读取真实工作树、修改代码、运行测试、分析日志和修复问题。
- GitHub：源码唯一事实来源，保存分支、Commit、PR、Tag、Release 和 CI 状态。
- Notion：保存项目状态、PRD、架构、数据库、重要 Hook、Bug、测试和发布记录。

## 自动触发

用户提出明确开发意图时自动进入本流程，例如：

- 开发这个插件
- 给某插件增加功能
- 修这个 Bug
- 开始开发 2.0
- 优化这个功能

不要求用户重复已有项目信息，也不再逐阶段询问是否继续。

## 完整闭环

```text
用户提出需求
→ 识别项目与任务类型
→ 读取 Notion 项目记录与开发规范
→ 读取 GitHub / 真实源码状态
→ 确认当前版本、分支、运行环境
→ 判断需求范围与风险
→ 更新 PRD / 开发任务
→ 确认 Hook、数据库、兼容方案和影响范围
→ 创建或选择开发分支
→ 调度 Codex / 可用开发工具修改代码
→ 快速自动测试
→ 失败则定位、修复、复测
→ 按风险触发安全 / 性能 / 兼容检查
→ 更新版本号与 CHANGELOG
→ Commit / Push / CI
→ PR、合并或发布准备
→ Notion 回写
→ 生成发布包 / Release 准备
→ 输出真实完成状态
```

## 上下文恢复

读取顺序：

1. 对应 Notion 项目页和已有 PRD。
2. Z-Blog 通用开发知识库与当前规范。
3. GitHub 当前仓库、默认分支、目标分支和真实源码。
4. 必要时读取 Issue、PR、Actions、Release 和 CHANGELOG。
5. 当前聊天中的最新明确要求优先于旧记录。

Notion 与 GitHub 记录冲突时，以真实代码和最新明确决策为准，并回写修正长期记录。

## 任务分类

自动判断任务属于新插件、新功能、Bug、性能优化、安全修复、数据库变更、重构、大版本升级或发布准备。

小 Bug 可走快速通道，不强制生成冗长 PRD。涉及架构、数据库、大版本、兼容性或多个模块时必须更新 PRD。

## 开发前确认

开发前必须确认：

- 当前插件版本和插件 ID
- 主要入口文件和 Hook
- 数据表与升级逻辑
- 受影响文件
- Z-Blog / PHP 兼容范围
- 是否影响现有数据
- 是否涉及权限、CSRF、SQL 或用户输入

禁止未读取现有代码就整体重写插件。

## PRD 与 Codex 任务

复杂任务的 PRD 至少包含：当前问题、目标版本、本次目标、包含范围、不包含范围、修改模块、Hook 变化、数据库变化、兼容方案、验收标准和测试要求。

Codex 必须基于真实项目状态开发，保持原有代码风格，优先 Z-Blog 原生机制，避免无意义封装和无必要文件。

## 代码开发原则

- 不直接修改 `zb_system` 核心文件。
- 优先使用官方 Hook / API / 模板机制。
- 保持代码简单、可维护。
- 修改范围尽量局限在当前需求。
- 数据库升级必须兼容旧版本数据。
- 高风险操作必须可回滚或有明确保护。

只有真实工具返回修改结果后，才可以标记为“已执行”。

## 快速自动测试

默认阻断检查只保留高价值项目：

- PHP 语法检查
- 本次功能核心测试
- 受影响数据库创建 / 升级检查
- 插件启用、停用及必要升级路径检查
- 关键 Hook 触发检查
- PHP Fatal / Warning / Notice 和 SQL 错误检查
- 后台写操作权限与 CSRF 检查
- 敏感信息误提交检查

失败时自动执行：定位错误 → 修改代码 → 重跑相关测试，直到通过或确认外部阻塞。

不要求每轮截图，截图只用于最终 UI 验收或视觉问题。

## 风险驱动检查

不再把所有重型检查设为每次必跑：

- SQL、权限、文件上传、外部请求：加强安全检查。
- 高频 Hook、日志、统计聚合：增加性能检查。
- 公共函数、架构、大版本：增加回归测试。
- PHP / Z-Blog 兼容变化：增加兼容矩阵。
- 正式发布前：执行发布级完整检查。

PHPStan、Semgrep、完整 PHPUnit 套件按项目和风险启用，不作为所有小修改的固定阻断门槛。

## Git 与 CI

开发完成后自动推进：

1. 检查 diff 和敏感文件。
2. 更新版本号和 CHANGELOG。
3. Commit。
4. Push 到开发分支。
5. 运行仓库已有 CI。
6. CI 失败则读取日志、修复、重跑。
7. 达到条件后进入 PR / 合并 / Tag / Release。

涉及合并主分支、正式 Release、覆盖线上文件等高影响动作时，按权限和风险规则执行。

## Notion 同步

Notion 从需求进入时就参与，需记录：

- 当前版本和状态
- PRD / 需求变化
- 重要技术决策
- 数据库和 Hook 变化
- 复杂 Bug 原因和修复
- 测试结果
- Commit / PR / Release
- 下一版本待办

普通代码 Diff 不复制到 Notion。

## 发布准备

- 核对 `plugin.xml` 版本
- 更新 CHANGELOG
- 检查安装 / 升级逻辑
- 检查发布包文件
- 排除 `.git`、日志、缓存、密钥、临时文件
- 准备 Tag / Release 信息
- 更新 Notion 发布记录

代码完成与正式发布分开记录。

## 自动执行与暂停条件

能通过当前工具完成的步骤直接执行，不反复询问。

只有以下情况才暂停：

- 外部平台要求本人授权
- 缺少密码、Token、服务器权限等关键凭据
- 涉及删除生产数据、覆盖线上数据库等不可逆高风险操作
- 当前 ChatGPT 工具无法连接必须操作的本地环境或 Codex

## 禁止模拟执行

必须区分：

- 已执行：有真实工具、Commit、CI、文件或记录可验证。
- 已规划：只生成方案、任务或命令，尚未真实执行。
- 外部待执行：需要 Codex、本机、服务器或当前未连接环境完成。

不得把计划描述为已经在 GitHub、Notion、Codex 或本机运行。

## 快速通道

明确的小 Bug、小范围 CSS / JS / PHP 修复可缩短为：

```text
读取真实代码 → 修复 → 相关测试 → Commit / CI → 必要时回写 Notion
```

数据库迁移、安全相关写操作和正式发布检查不能使用快速通道跳过。

## 完成标准

一次开发任务只有在以下状态都明确后才算闭环：

- 需求状态明确
- 真实代码状态明确
- 测试结果明确
- Git 状态明确
- Notion 状态明确
- 发布状态明确
